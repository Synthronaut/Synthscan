# People and Buyer alerts

Open SynthScan's desktop Home window. The sidebar now has **People** and
**Buyer alerts**, alongside the existing pages. Your HUD modes and placement
remain unchanged.

## People

People loads names from the current shard's server-member group. The page shows
the last refresh time and any service error; this list is not a verified player
population counter. It refreshes about every 30 seconds while viewed, or while
at least one saved player has appearance alerts enabled. With no enabled player
alerts and the page closed, it stops automatic roster requests.

Type in the top box to filter names or tags. **Search handles** searches the
account service for an RSI handle independently of the roster. The source menu
switches between shard members, search results and saved player tags.

Your own row is **royal purple**, taking priority over party and friend colors.
Confirmed friends are highlighted **green**; other current party members are **blue**.
Party blue takes priority for someone who is also a friend. The Relationship
column identifies both memberships. These colors use read-only game-service
relationship data, independently of custom tags such as Friendly. Relationship
data refreshes roughly once a minute while People is open; **Refresh shard**
checks it sooner. Unavailable or stale relationship data stays neutral.

Background status updates leave the list untouched. When membership or tags do
change, the list preserves its top visible player, scroll offset and selected
identity, including unsaved tag text. If the player at the top leaves, the next
surviving neighbour stays in view. Explicit filter/source changes reset the view.

Add players to the Action list to assign **Aggressive**, **Trader**, **Friendly**,
**Org**, **Org Affiliate**, **Crew**, **Buyer**, **Avoid**, or a custom tag. Use
**Add tag** to apply the selected category directly. Both tag dropdowns put
**Org** first and **Friendly** second, followed by the remaining tags alphabetically.
The labeled **Custom tags** field lets you type several comma-separated tags;
select **Apply tags** to save those. Tags are user-assigned local notes, not assessments
generated by SynthScan. **Alert on appearance** is independent of the categories.

Each tag appears as its own colored chip in both player lists, separated by a
small gap. Org stays orange; Friendly is green, Aggressive red, Trader cyan,
Org Affiliate yellow, Crew violet, Buyer blue, and Avoid pink. Custom tags also
receive individual colors. Tag colors stay the same when a player has several
tags or their row is selected. Long sets expand the tag column and remain
available using the table's horizontal scrollbar.

The left pane is the live player roster. Names and tag columns have bounded
widths so the second pane can hold a separate **Action list**. Click a player's
row to highlight it; click it again to deselect. Other highlighted rows stay
selected without holding Ctrl or Shift. Press **Add to actions →** to move the
chosen names into the Action list. Clicking or double-clicking a name never adds
it directly.
Adding the same player again does not create a duplicate. Roster filters,
searches and refreshes do not clear the Action list. Its contents survive an app
restart within the same joined game session.

**Add org →** adds current shard members tagged Org or Org Affiliate. Select a
preset or custom tag in the right-hand dropdown and choose **Add by tag** to add
all current shard members carrying that exact tag. This does not send requests.
Use the Action list's checkboxes and **Remove selected**, or **Clear actions**,
to exclude players before taking a bulk action. These operations do not remove
their saved tags. This feature is strictly current-shard-only; there is no
off-shard/all-saved-players mode. Confirmed roster updates remove players no
longer reported on the shard. A new joined game session starts an empty list.

The controls under the Action list apply to everyone in it. Choosing **Org** and
**Add tag** adds Org while preserving other tags, using the same control as every
other category. For multiple players, **Apply tags** adds the typed
tags without replacing existing ones, and preserves individual alert settings.
**Clear tags** removes their tags. Join alerts can be edited for one staged player
at a time. The list is locked while a request queue runs; cancel it before
changing recipients. The roster remains available for browsing.

**Invite all party…** and **Add all friends…** review the Action list in a
scrollable confirmation before sending anything. Shard membership is rechecked
immediately before either kind of write; departed players are skipped. Current
party members/already accepted friends, and players previously attempted in this
game session are skipped. Requests are sent serially, with a freshly sampled
**random 0.09–0.99-second gap after each completed request**. The page shows sent, skipped
and remaining counts, plus a countdown. **Pause / Resume** and **Cancel** control
the remaining queue; a request already in flight can finish. **View queue**
updates live and also provides queue controls. Pausing and resuming rechecks
membership before the next invitation.
An unsuccessful or uncertain invitation stops remaining sends, with no automatic
retry. **View queue** lists receipts, skips, and unattempted players. A sent
invitation still requires the recipient's acceptance. Changing shards clears the
batch results. Attempt history is saved locally in `party_invite_attempts.json`,
before each attempted send, and survives an app restart within the same joined
game session. Friend requests have separate history in `friend_request_attempts.json`.
To send another request to a previously attempted recipient, explicitly check
**Repeat previously attempted requests this session** in the
recipient confirmation. The checkbox defaults off. This includes unconfirmed
attempts, which should be checked in-game before retrying. A new game session
starts a new history. The queue adds no idle network polling.
Closing the app or changing game sessions stops the remaining batch after any
invitation already in flight.

These controls reduce burst traffic and accidental repeat invitations. The pace
is a product choice, not a CIG-approved threshold or a guarantee about enforcement.

Appearance alerts mean the player appeared in a new server-group snapshot. They
do not prove an exact join time or online status. Startup, session changes and
recovery after failed or long-delayed reads establish a quiet baseline. A single
missing snapshot does not generate a repeat arrival alert. Notices appear briefly
at the lower-left of the game and remain in the desktop notice history.

**Add all friends…** and **Invite all party…** are separate buttons. Each presents the
recipient list for confirmation, rechecks each identity and the current
shard, and submits one request per eligible recipient. The UI distinguishes a returned request receipt
from acceptance by the other player. Direct non-friend party invitation, server
permissions and social limits are decided by the game service. Outgoing actions
have passed mocked protocol tests. The user has also reported a successful live
party invitation. Batch invitations were verified with mocks; development tests
do not send invitations to real players.

If a result is uncertain, the app asks you to check in-game before retrying;
it does not automatically repeat outgoing requests. Normal game sign-in is needed.

## Buyer alerts

Search for a material or item and choose the exact UEX entry, including Pure
versus non-Pure variants. Set quality (for example **1000**; **0** means any),
and optionally a minimum price and its exact listing unit. Select **Watch buyers**.

Existing buy ads populate quietly. Subsequent checks run every **30 minutes**
and alert once per newly observed eligible ad. **Refresh now** checks sooner.
Duplicate saved watches are rejected, and overlapping watches do not generate
multiple alerts for the same newly observed ad. Seen IDs persist across app
restarts. Missing or ambiguous quality cannot satisfy an exact-quality watch.
Minimum-price filters only compare advertisements with the specified unit.

Select a saved watch and **Show matches** to inspect its current eligible ads.
**Open selected UEX ad** opens the selected listing. **Show notices** restores
the shared notification history. Watches can be paused, resumed or removed.
When there are no enabled watches, this feature stops making UEX listing requests.

UEX data is community maintained. Active-ad polling cannot recover an ad which
appeared and disappeared between checks or while the app was closed. A feed cap
can limit coverage. Listing edits do not repeat an alert for the same seen ID.
The feature does not publish ads, contact buyers or perform transactions.

## Performance and storage

These features reuse the existing independent background worker. Network calls
run on a bounded two-worker pool and do not block the native UI or session ribbon.
No new game screen capture, OCR or GPU tracking is used. Name lookups are batched
and cached for the current roster. Private tags, watch definitions, seen-ad IDs,
action receipts and notice history stay in the local SynthScan profile and are
excluded from public packaging. A specific FPS overhead has not been measured.

## Friends, invitation results and retries

**Friends** in the source menu shows verified game contacts, including resolved
friends outside the current shard. **Add friends →** stages that list in Actions;
choosing **Friend** in Add by tag does the same. Other tag-based additions stay
limited to current shard members. Unavailable names are reported, not invented.
The automatic **Friend** chip is bright emerald; custom **Friendly** is pale mint.
Friend reflects the latest friends-list read and cannot be assigned as a custom tag.

**Invite to party** and **Send friend requests** submit the reviewed Action list
directly. There is no extra confirmation dialog. A fresh deliberate click can
retry a previous session attempt; duplicate command IDs and overlapping queues
remain blocked. The outstanding random delay carries across consecutive queues.
Each friend-request or party-invitation batch is limited to **50 recipients**.
Larger selections are rejected in full before sending; they are never silently
truncated or split into several batches. The **Action list itself holds at most
50 people**, shown as a count out of 50. Add by tag and Add friends fill only the
remaining spaces, keep existing entries, and report how many did not fit.
Duplicates do not consume another space. Remove names to make room for others.
Invitations to other shards are permitted only for verified friends, and the
worker rechecks that relationship before sending. No automatic retry is added.

Rows show Friend and Party results separately. A green check means the game
service returned a successful send receipt, not that the recipient accepted.
Amber caution marks indicate failed, skipped or unconfirmed attempts with their
reason. Already-friend/already-party outcomes are neutral. Queued requests never
receive a success check. Results persist for the same game join and reset on a
new join; older unrecorded requests are not reconstructed.
